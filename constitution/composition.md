# composition — manifests, load timings, summon

How a workspace declares what it is, and what a conforming engine does with the declaration. Extracted from the router's lived dispatcher protocol (the prose form remains in the router's `CLAUDE.md`; this is the normative form an engine implements).

## 1 · The manifest

- **C-1** A workspace's composition is **declared, not discovered**: the engine knows a module or protocol exists because `modules.toml` (+ the private overlay `modules.local.toml`) names it. Engines MUST NOT scan for modules.
- **C-2** Module kinds: `[[operators]]`, `[[commons]]`, `[[repos]]` — each entry `{name, path, repo?, note?}` — and `[[protocols]]` entries `{name, source, load, when?, requires?}`. Legacy section names `[[models]]` and `[[agents]]` MUST parse as `[[operators]]` during the 2026-07-24 rename migration; declared legacy `models/` paths are honored as written.
- **C-3** Commented-out manifest entries are examples and MUST NOT be treated as declarations. Any composition summary shown or injected MUST be **byte-derived** from the manifests — an engine never asks the model to re-derive the composition. *(The gemma confabulation, made structurally impossible.)*
- **C-4** Everything is presence-gated: a bare clone declares nothing, composes nothing, and is a working host — not an error. A missing `requires:` dependency means *skip the protocol*, not fail.
- **C-5 (stability marker — the protocol interface is provisional).** The `[[protocols]]` shape deliberately models exactly one axis: `load` — *when* a protocol fires. It does NOT model what **kind** of thing a protocol is — a lens the session sees through, a hard rule, a gate, a clock, a declared spectrum, or mechanisms not yet invented — because that dimension is undesigned, and the ways of shaping model behaviour are still being gathered (David, 2026-07-24: *"there are so many different ways to nudge model behaviour and I'm wary of collapsing our methodology too fast, too early"*). Engines MUST treat the protocol declaration as subject to extension and MUST NOT reject manifests carrying unknown protocol fields; nothing in this standard may be built in a way that assumes the current shape is final. When protocol kinds are *earned* — by lived use, not symmetry — they arrive as a versioned extension here. *(Candidate decomposition and its unearned status: `zojercommons/projects/harness/nuggets.md § G` — protocol kind is an unmodeled dimension.)*

- **C-6** The private overlay (`modules.local.toml`) merges with `modules.toml` **additively, per section**: entries from both are concatenated, base first then overlay, preserving declaration order within each. A `name` collision **within a section** is an **error** — an engine MUST refuse the composition rather than silently override, or silently duplicate. This holds **within a single manifest as well as across the pair**: two entries sharing a `name` in one file are as ambiguous as two across files, and the C-2 legacy path produces exactly that shape without anyone writing a name twice — `[[models]]` and `[[operators]]` both declaring an operator during a rename, which the compat symlink then resolves to one directory. An ambiguous composition is not a composition, and a boot that quietly picks one of two candidates cannot be trusted about what it loaded. *(Ratified 2026-07-26. The rule had gone undefined because the two files have never overlapped — `modules.toml` ships only commented-out examples while `modules.local.toml` carries every real entry — so defining it changed no existing workspace's behavior. Surfaced by writing the second implementation, which is the intended direction: the engine reveals an untested rule, and the rule lands in the standard rather than being settled quietly inside a crate.)*

## 1a · The `[router]` table

`[router]` is a singleton table, not a module — the minimal core that IS the workspace, never composed and never a `[[...]]` entry. `contains` is the router's own allowlist, the same list the workspace's gitignore mirrors. `boot` names one file, relative to the workspace root, read once at instance creation — this is the router's OWN boot file, distinct from a module-contributed `[[protocols]]` entry with `load = "boot"` (C-5, § 2 L-1), which carries protocol semantics (`requires`, load timing, companion data) that the router's own file does not need. An absent `[router]` table is a working manifest (C-4): nothing about `contains` or `boot` is required. The private overlay merges `[router]` field-wise rather than wholesale — `boot` from the overlay wins if present, otherwise the base's `boot` carries through, and the same holds for `contains` — because a machine-local overlay setting one field must not silently erase the other. Like the `[[protocols]]` shape (C-5), `[router]` is provisional: an engine MUST NOT reject a manifest carrying unknown keys inside `[router]`.

## 2 · Load timings

- **L-1** `load = "boot"` — the body is read at session start and composes the starting context.
- **L-2** `load = "on-demand"` — registered as a pointer (`name` + `when`); the body MUST NOT be read until the work matches `when`. Lazy by design: anything auto-loaded becomes a write-attractor.
- **L-3** `load = "session-end"` — best-effort at close, and **best-effort is normative**: a clean close is not promised, so nothing that must persist may rely solely on a session-end protocol. Durability requires a threshold-fired or boot-time path beside the close-time one.

## 3 · Summon

- **B-1** An explicit `@<operator>` summon boot-gates the turn: the summoned operator's boot protocol runs **first**, before any repo, skill, or tool touch except the dispatcher itself — even when the same message names a destination. The destination is material to orient *through*, not a reason to skip orienting.
- **B-2** Where the engine can enforce (hooks, system-prompt injection, pre-tool gates), summon-boot is **deterministic**: the engine reads the operator's boot doc itself and injects it with an authoritative framing, re-asserted per turn so it survives compaction. Boot-gating that depends on the model choosing to comply is advisory and does not satisfy this rule. *(instances.md S-3 applies.)*
- **B-3** A summon of a name not declared in the manifest is a no-op, not an error. One boot per (session, operator).
- **B-4** Injected boot content MUST state its **path anchor** — the operator's root, and how bare relative paths resolve under it — rather than leaving path resolution to model inference. *(The anchor finding from the weak-pilot bench.)*

## 4 · The scope guardrail

- **G-1** This constitution holds only rules that are true **regardless of which modules are composed**. A rule specific to an operator, a commons, a repo, or a person belongs to that module's own protocols, at its own tier (workspace → operator → collaborator). An engine MUST NOT require a workspace to reorganize around it — each stage lands in the household.
